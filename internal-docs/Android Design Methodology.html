Первое впечатление: наука о визуальном восприятии

Мозг обрабатывает визуальный образ быстрее, чем успевает прочитать ни одного слова. Это не метафора — это измеримая нейробиология.

50 мс
время формирования первого визуального суждения об интерфейсе
Lindgaard et al., 2006 — первое peer-reviewed измерение "first impression" в digital
17 мс
обновление зрительного восприятия (1 кадр @ 60fps) — минимальный порог для "живого" UI
Human Vision Research, MIT Media Lab
38%
пользователей уходят, если макет некрасив или неудобен
Adobe State of Content Report, 2018

Что формирует первое впечатление

  • 1
    Цветовая гармония и общий тон
    Первое, что видит мозг — не текст и не иконки, а цветовой "настрой". Тёплые нейтральные с акцентом ≠ холодный серый. Выбор палитры — это первая секунда.
  • 2
    Визуальная иерархия и "вес"
    Что самое тяжёлое на экране? Если ответ не очевиден за 1–2 секунды — иерархия не работает. Один доминирующий элемент на экран.
  • 3
    Баланс и плотность
    Слишком плотно — тревожно. Слишком пусто — дёшево. "Дорогие" приложения используют больше белого пространства, чем кажется необходимым.
  • 4
    Консистентность форм
    Скруглённые углы одного радиуса читаются как "система". Разные радиусы — как несобранность. Один shape-токен на все карточки.
Ключевое: На первое впечатление у дизайна есть 50ms. За это время мозг не успевает прочитать ни слова, не успевает понять структуру — он оценивает исключительно визуальную привлекательность: цвет, пропорции, "плотность" и общий тон. Пишите эти параметры сознательно.

Material 3 Color System: как работает

  • HCT
    HCT color space
    Hue–Chroma–Tone. Более равномерный перцептивно, чем HSL. Один seed (#6B5CE7) → полная light+dark система с гарантированным контрастом. Используй Material Theme Builder.
  • ✓
    Семантический цвет = состояние
    Зелёный = хорошо, жёлтый = умеренно, красный = требует внимания. Oura-паттерн: цвет говорит о состоянии до того, как пользователь прочитал цифру. Моментальное считывание.
  • ✓
    Максимум 3 акцентных цвета в UI
    Primary accent (действия, CTA), Semantic positive (green), Semantic warning (amber). Всё остальное — нейтральные. Больше 3 акцентов = хаос иерархии.
  • ✗
    Не ставь насыщенный цвет на большие поверхности
    Насыщенный #6B5CE7 работает на кнопке. На фоне карточки — утомительно. Используй tonal variants (10–15% opacity от primary) для контейнеров.

Tonal elevation в dark theme

Критично для премиального dark mode: В Material 3 тени в тёмной теме заменяются тональным цветом. Surface → Surface+1 → Surface+2... каждый уровень добавляет ~5–10% первичного цвета в overlay. Это то, что отличает "дорогой" dark mode от просто тёмного фона. Без этого все карточки сливаются.
Surface elevation tokens — Kotlin/Compose
// В MaterialTheme dark = true, elevation создаёт tonal overlay автоматически // Surface+1 ≈ 5% primary, Surface+2 ≈ 8%, Surface+3 ≈ 11% Card( modifier = Modifier.fillMaxWidth(), elevation = CardDefaults.cardElevation(defaultElevation = 2.dp) // → Surface+2 в dark ) { ... } // Для явного контроля: Surface( color = MaterialTheme.colorScheme.surfaceColorAtElevation(4.dp) ) { ... }

Выбор шрифта: правила

  • ✓
    Display + Body = Серьёзный контраст
    Serif display + sans-serif body. Или variable sans с экстремальной разницей в weight (300 vs 700). Слабый контраст — шрифты "борются". Сильный контраст — система читается.
  • ✓
    Display: один момент на экран
    Display Large — это дизайнерский элемент, не просто крупный текст. Утреннее приветствие, ключевая метрика, score. Используется редко, но создаёт "момент". Oura, Calm, Focus Friend — все делают так.
  • ✓
    Tabular numbers для метрик
    font-variant-numeric: tabular-nums — цифры одинаковой ширины. Без этого "214" при обновлении прыгает по ширине. Обязательно для любых счётчиков, таймеров, прогресс-значений.
  • ✗
    Не более 2–3 начертаний на экран
    Display + Body + Label. Больше — хаос. Label для uppercase микротекста (категории, временные метки), body для всего читаемого, display для "моментов".
  • ✗
    Не используй system font по умолчанию для brand moments
    Roboto/Inter системный — хорош для тела. Для приветствия, для score, для ключевых цифр — кастомный serif или variable font создаёт характер и "дорого".

Пространство: воздух как инструмент

Белое пространство — не "пустое место". Это дизайнерский элемент с измеримым эффектом на восприятие качества и читаемость.

+20%
рост понимания контента при правильном использовании white space
Lin, D., Journal of Information Science, 2004
8dp
базовая единица сетки Material Design. Всё кратно 4dp, ключевые элементы — 8dp
Material Design Spec, Google 2023
16dp
минимальный боковой отступ экрана. Меньше — контент выглядит зажатым
Material Design Spacing System

Правила пространства

  • 8×
    8dp grid
    Все отступы кратны 4dp, "эмоциональные" отступы (между секциями, после заголовков) кратны 8dp. Это создаёт ритм, который воспринимается как порядок даже если пользователь не формулирует почему.
  • ✓
    "Дорогие" приложения используют больше пространства, чем кажется нужным
    Calm, Oura, Apple Health — все используют щедрые отступы. Плотность = дёшево. Воздух = premium. Если экран кажется "недозаполненным" — скорее всего, он правильный.
  • ✓
    Внутренний отступ карточки: 16–20dp
    padding: 16dp минимум на телефоне. Меньше — контент внутри карточки выглядит зажатым. Для featured карточек (hero) — 20–24dp.
  • ✓
    Разные gap между разными уровнями иерархии
    gap между элементами одной карточки: 8dp. Между карточками: 12dp. Между секциями: 24–32dp. Градация gap = визуальная иерархия разделов.
  • ✗
    Не заполняй пустоту декоративными элементами
    Рефлекс заполнить "пустое место" разделителями, иконками, фоновыми паттернами — вреден. Пустота работает. Декоративный шум снижает качество восприятия.

Анимация: физика и намерение

Анимация — не украшение. Это коммуникация: она объясняет, что произошло, что произойдёт, и помогает пользователю удерживать контекст.

Правило: Анимации UI должны завершаться до того, как пользователь захочет сделать следующее действие. Если анимация заставляет ждать — она слишком долгая. Если её не заметно — слишком короткая. 200–300ms — золотая середина.

Spring Physics vs Linear — почему пружина лучше

  • →
    Linear/Cubic bezier
    Механическое, предсказуемое. Ощущается как машина. Нет "веса" у объектов — они перемещаются одинаково независимо от размера.
  • ✓
    Spring animation
    Имитирует физику реальных объектов. Элемент "знает" свою массу. Большой элемент двигается медленнее (higher stiffness required). Создаёт ощущение материального мира. Именно это делает iOS и M3 ощущением "живыми".
Spring параметры — Jetpack Compose
// Основные пресеты для разных случаев // Кнопка / tap feedback — быстро, упруго val snappy = spring( dampingRatio = Spring.DampingRatioMediumBouncy, // 0.5 stiffness = Spring.StiffnessHigh // 10_000 ) // Карточка появляется — плавно val smooth = spring( dampingRatio = Spring.DampingRatioNoBouncy, // 1.0 — без отскока stiffness = Spring.StiffnessMediumLow // 200 ) // Hero transition / большой элемент — медленнее, с характером val hero = spring( dampingRatio = 0.8f, stiffness = 120f ) // Счётчик метрики val animatedValue by animateFloatAsState( targetValue = steps.toFloat(), animationSpec = tween(800, easing = FastOutSlowInEasing) ) Text("${animatedValue.roundToInt()}", fontFeatureSettings = "tnum")

Ключевые анимационные паттерны

  • ✓
    Staggered list entry
    Элементы списка появляются один за другим с delay index×50–70ms. Визуально читается как "загрузка по порядку" — не всё разом. Создаёт ощущение живости и намерения.
  • ✓
    SharedTransition (card → detail)
    Карточка буквально "превращается" в детальный экран — shared element transition. Пользователь не теряет контекст откуда он пришёл. Jetpack Compose: SharedTransitionLayout + sharedElement modifier.
  • ✓
    Haptic feedback на значимых действиях
    Medium impact на завершение (чек-ин, задача выполнена). Light impact на selection. Никогда — на каждый tap. Вибрация на каждый tap раздражает; на значимый момент — усиливает удовлетворение.
  • ✗
    Не анимируй то, что не несёт смысла
    Анимации ради анимаций (spinning loaders вместо прогресса, bounce на статичном тексте) — noise. Каждая анимация должна отвечать на вопрос: "что она объясняет пользователю?"

Зоны доступности большого пальца

Легко доступно
Растяжка
Трудно
  • ✓
    CTA и навигация — в нижней зоне
    Кнопка "Начать день", check-in buttons, bottom navigation — всё ниже центра экрана. Большой палец туда достаёт без усилий.
  • ✓
    Контент — в верхней половине
    Читаемый текст, карточки с данными — пользователь смотрит, не нажимает. Можно размещать выше.
  • ✗
    Деструктивные действия — не в зоне случайного касания
    Удаление, отмена, "Нет" — не прямо под большим пальцем в рабочем состоянии. Нужен step-away от привычного места тапа.

Bottom Navigation: данные

Bottom nav увеличивает: Task completion rate, time-on-task (меньше ошибок навигации), thumb comfort score. Google рекомендует 3–5 destinations. Для нашего приложения — 3: Today / История / Профиль. Меньше = фокус. Больше = confusion.
  • 3
    Максимум 3–5 вкладок
    3 — оптимум для companion app. Today (дом) + История + Профиль/Настройки. Каждая вкладка — отдельный "режим", не просто разный контент.
  • ✓
    Active indicator M3
    M3 bottom nav использует pill-shaped active indicator на текущей вкладке. Это стандарт — не изобретай свой. Пользователи узнают его мгновенно.

Загрузка: управление временем

Пользователь не ждёт — пользователь интерпретирует. Одни и те же 2 секунды ощущаются по-разному в зависимости от того, что происходит на экране.

Google/SOASTA "The State of Online Retail Performance", 2017
−15%
снижение воспринимаемого времени ожидания при skeleton screen вместо spinner
Medium Engineering Research, 2017
0.4 сек

Порядок выбора индикатора

  • <400
    <400ms — никакого индикатора
    Данные появляются мгновенно. Indeterminate spinner на <400ms — UX-mistake: он "обнажает" задержку там, где её никто не заметил бы.
  • 1–3s
    1–3 секунды — skeleton screen
    Показывает layout-форму будущего контента. Пользователь видит структуру заранее. Shimmer-эффект: синхронизированный на весь экран (не покарточно). Создаёт ощущение, что загрузка вот-вот завершится.
  • 3s+
    >3 секунд — percentage progress
    Если операция долгая (первый запуск, большой файл) — реальный progress bar с %. Неопределённый spinner на 10 секунд невыносим. Человек хочет знать "сколько ещё".
  • ✓
    Branded Lottie для первого запуска
    Вместо белого экрана при первом открытии — маленькая анимация 1–2 секунды. Устанавливает personality и создаёт первое впечатление о качестве. 10–50кб Lottie JSON против 500кб GIF.

Онбординг: от установки до ценности

77% пользователей удаляют приложение в первые 3 дня. Онбординг — единственный шанс показать ценность до того, как пользователь уйдёт.

Принципы onboarding

  • ✓
    Value-first, permission-second
    Сначала объясни ценность разрешения — "Чтобы прогноз был точным, нам нужен доступ к Health Connect" — потом системный диалог. Никогда не бросай системный диалог "вслепую".
  • ✓
    Одна задача за один шаг
    Не кидай 5 запросов разрешений подряд. Один шаг — одно разрешение. Наш онбординг: 3 шага, по одной задаче. Правильно.
  • ✓
    Graceful degradation — не блокируй при отказе
    Пользователь отказал в Health Connect? Хорошо — работаем без сна и шагов. Не показывай error screen, не блокируй онбординг. Скажи что именно не будет работать — и продолжай.
  • ✓
    Aha moment в первый сеанс
    До того как попросить ещё что-то — дай один insight. Для нашего приложения: показать время экрана за вчера + короткий прогноз. "Вот что мы можем" → хочется дальше.
  • ✗
    Не делай пропускаемый туториал
    "Skip tutorial" в правом верхнем углу — признание что туториал скучный. Если продукт требует обучения — сделай его частью первого опыта, не отдельным блоком.

Dark Mode: OLED и ночная аудитория

Dark mode — не тренд. Это часть Android OS, которой пользуется большинство активных пользователей. И это физика: тёмные пиксели на OLED потребляют меньше энергии.

91%
Android-разработчиков имплементировали dark mode (сравн. 77% iOS)
Android Developer Survey, Google I/O 2023
−63%
потребление батареи OLED-дисплея при полностью чёрном экране vs белом при яркости 100%
Google Android Team Energy Study, 2018
58%
пользователей используют dark mode на телефоне (опрос 2024)
Android Authority User Poll, 2024

Dark Mode: правила реализации

  • ✓
    Tonal elevation вместо теней
    В тёмной теме тень на тёмном фоне невидима. M3 решает это через tonal overlay: чем выше elevation, тем светлее поверхность. Card(elevation=2.dp) автоматически светлее поверхности фона в dark mode.
  • ✓
    Не инвертируй — переопределяй
    Наивная инверсия (#FFFFFF → #000000) ломает контраст и иерархию. Нужна отдельная семантическая система токенов для dark: background не #000, а #0F0F11 (чуть теплее = комфортнее).
  • ✓
    Акцент: проверь на dark bg
    Primary #6B5CE7 на тёмном фоне может быть слишком тёмным. В dark mode акцент часто нужно осветлить (PrimaryLight: #9B8AFF или #8070FF). Проверяй контраст в обеих темах.
  • ✗
    Не используй чистый #000000
    Абсолютный чёрный (#000000) на OLED выглядит "дырой" рядом с тёмно-серыми элементами. Используй #0F0F11 или #111009 — слегка тёплый, менее резкий.

Консистентность: доверие через повторение

Консистентный интерфейс снижает когнитивную нагрузку. Пользователь тратит меньше усилий на "разгадывание" UI и больше — на задачу.

−42%
снижение ошибок пользователей при консистентном UI (одинаковые паттерны для похожих действий)
Nielsen Norman Group, Consistency in UX, 2020
3
радиуса скругления максимум на весь дизайн. Больше — "несобранность". М3 рекомендует shape-токены
Material Design 3 Shape System

Design tokens: что стандартизировать

ТокенЗначениеГде применяется
shape.card16dpВсе карточки на HomeScreen
shape.button14dpCTA кнопки, action кнопки в уведомлении
shape.chip8dp (или circular)Теги, статусные чипы
elevation.card2dpВсе карточки (tonal в dark)
spacing.screenPadding20dpГоризонтальный отступ всего контента
spacing.cardPadding16dpВнутренний отступ всех карточек
spacing.sectionGap24dpМежду секциями HomeScreen

Что должно быть идентичным по всему приложению

  • ✓
    Все карточки — один радиус, один elevation
    Не карточка с 12dp и другая с 16dp. Не карточка с тенью и другая без. Один токен, применённый везде — это "система".
  • ✓
    Один тип кнопки для CTA
    Primary action = FilledButton с Primary цветом. Secondary = OutlinedButton. Never mix. Пользователь учит один раз: "фиолетовая кнопка = главное действие".
  • ✓
    Temporally consistent feedback
    Нажатие на любую кнопку → один и тот же scale animation (0.95f, 150ms). Не три разных "нажатых состояния" на три типа кнопок. Один паттерн — привычка.

Health App паттерны: специфика категории

Health и wellness — отдельная категория с собственными исследованными паттернами. Нарушение любого из них снижает engagement даже при хорошем общем дизайне.

66 дн
среднее время формирования привычки (не 21 день). Приложение должно удержать на этот срок
Lally et al., European Journal of Social Psychology, 2010
+25%
рост долгосрочного retention при наличии streak-механики в health apps
Duolingo Internal Research / продублировано в Loop Habit Tracker UX study
5 сек
максимальное время check-in взаимодействия для высокого completion rate (Daylio modell)
Daylio UX Research via App Store Reviews Analysis

Паттерны лучших health apps

  • ✓
    Personal baseline, не population norm
    "Твой обычный результат 7.2ч сна" vs "Рекомендуется 8ч". Personal comparison = мотивация без осуждения. Oura и наш LLM-промпт уже так делают. UI должен это отражать: "—40 мин от твоего обычного", не "—40 мин от нормы".
  • ✓
    Zero-friction check-in
    3 кнопки прямо в уведомлении. Нажал — готово, приложение не открывается. Daylio: 5 секунд. Наш чек-ин уже так устроен — это правильно.
  • ✓
    Позитивное подкрепление, не только критика
    Замечать хорошие отклонения, не только плохие. "Вчера ты взял телефон на 20 мин позже — хороший сигнал" работает лучше чем всегда указывать на проблемы. LLM-промпт уже учитывает это (правило 4 в системном промпте).
  • ✓
    Прогрессивное раскрытие данных
    Oura: 3 уровня глубины. Уровень 1: один aggregate score. Уровень 2: breakdown по категориям. Уровень 3: raw data + trends. Новый пользователь не перегружен деталями, advanced user получает нужное.
  • ✓
    Semantic color для здоровья
    Выдели отдельные цвета для состояний: зелёный (хорошо), жёлтый (умеренно), красный (требует внимания). Эти цвета ТОЛЬКО для health-состояний — не для UI-акцентов. Смешивание = confusion.
  • ✗
    Не перегружай главный экран данными
    Соблазн показать всё собранное — экран на 12 метрик. Результат: пользователь не знает на что смотреть. Максимум 4–5 метрик в "fold" (видимая область без скролла).

Character-driven design: почему работает

Focus Friend (Google Play Best App 2025): Один анимированный персонаж "Bean", который реагирует на состояние фокус-сессии. Никаких лишних фич. Это и есть причина победы.

Emotional design создаёт retention, который feature-list не создаёт. Люди возвращаются к приложениям, которые ощущаются "живыми". Replika, Wysa, Headspace — все используют это.
  • ✓
    Один персонаж/элемент, реагирующий на состояние
    Небольшой Lottie-элемент (64–96dp) в верхней части HomeScreen, который медленно "дышит" в спокойный день и активно пульсирует в энергичный. Меняет speed через LottieAnimatable.speed по readiness score.
  • ✓
    Утреннее сообщение как "разговор", не как данные
    Текст прогноза — это голос компаньона, не отчёт. Тёплый тон, первое лицо от приложения. Рамка "текст в карточке" vs "текст в bubble" — bubble ощущается как диалог.

Чеклист: приоритизированный список

Всё вышеперечисленное — в конкретные задачи. Три уровня: Must Have, Should Have, Nice to Have.

🟢 Must Have — без этого нет "красивого"

M1
Tonal elevation в dark mode

Card elevation=2dp на тёмном фоне. Без этого карточки сливаются с фоном в dark mode.

M2
Skeleton loading на HomeScreen

Shimmer вместо spinner пока грузятся данные. 3 строки кода с compose-shimmer.

M3
Spring animation на кнопках

scale 0.95f + spring(stiffness=High) при press. Haptic Medium на check-in. 5 строк кода.

M4
Tabular numbers на метриках

fontFeatureSettings = "tnum" на все числа (шаги, минуты экрана, сон). Цифры не прыгают при обновлении.

M5
Display Large для утреннего приветствия

MaterialTheme.typography.displayMedium.copy(fontWeight=Light). Это момент, не подпись.

M6
Consistent shape tokens

Один радиус на все карточки (16dp), один на кнопки (14dp). Никаких вариаций "на глаз".

M7
Semantic colors для health states

Зелёный chip если данные хорошие, жёлтый если средние, красный если плохие. Отдельно от Primary.

🟡 Should Have — сильно улучшит восприятие

S1
Animated character / element

Lottie-элемент на HomeScreen, реагирующий на readiness (speed от 0.5x до 2.0x). Focus Friend-паттерн.

S2
Staggered list entry

Карточки появляются с delay index×60ms. AnimatedVisibility + fadeIn(tween(delayMillis = index * 60)).

S3
Counter animation на метриках

animateFloatAsState(tween(800)) при первом показе. "214 мин" считает вверх от 0 — earned feeling.

S4
Empty state для первого запуска

Lottie + "Носи телефон сегодня — утром появится первый прогноз". Не пустой экран.

S5
SharedTransition card → detail

SharedTransitionLayout при переходе из карточки утреннего сообщения в полный экран.

S6
Display-шрифт для ключевых моментов

Fraunces / Playfair для приветствия и score. Inter/Roboto для всего остального.

⚪ Nice to Have — polish уровня App Store Featured

N1
Ambient background animation

Медленно меняющийся gradient на HomeScreen в зависимости от времени суток (утро = тёплый, ночь = прохладный).

N2
Sparkline-графики на метриках

Tiny 7-дневный sparkline под каждой метрикой. Тренд визуально без отдельного экрана.

N3
Glance Widget

Виджет на рабочий стол с утренним прогнозом. Пользователь видит данные не открывая приложение.

N4
Personalised greeting с именем

"Доброе утро, Александр" при наличии имени. Display Large. Пользователи помнят это.

Финальное правило: "Premium — это тонкий слой polish поверх обычного layout." Большинство M–Must Have задач — это по 5–15 строк кода. Совокупный эффект: приложение начинает ощущаться как продукт, а не как студенческий проект.
