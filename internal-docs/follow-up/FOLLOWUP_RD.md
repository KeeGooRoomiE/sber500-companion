# Follow-up: длинные цепочки, связность, дрейф — результаты

Задача #7 из `internal-docs/dev/LLM_EVAL_TASKS.md`: «генерить длинные цепочки follow-up,
скорить связность/дрейф, найти где деградирует». Инструмент: `tools/followup-rd/`
(fetch → chain → judge_drift), переиспользует `research.py`/`audit.py` из соседних tools/.
Строго последовательно: одна модель за раз.

**Апдейт (задача #2, `internal-docs/models/MODEL_COMPARISON.md`):** третья модель, gpt-5.1
(лучшая по latency/cost/reliability), прогнана через тот же пайплайн — **76% halluc (16/21)**,
тот же паттерн confabуляции на `prev_days`/`similar`/`retrieval`, что у gigachat. Вывод ниже
про «проблема дисциплины модели» остаётся верным для claude-sonnet-4.6 как исключения, но
нужно читать шире: **это в первую очередь структурная проблема промта** (нет данных по дням
для этих вопросов), которую смена модели решает лишь частично — claude-sonnet справляется
хеджированием, а не наличием данных. Промт-фикс нужен независимо от выбора модели.

---

## Структурная поправка (до результатов)

В проде follow-up **не цепочка**: `backend/internal/llm/followup.go::BuildFollowup` каждый
раз грузит заново только оригинальный инсайт+данные, без памяти о предыдущих follow-up-ответах
(явный анти-дрейф дизайн по комментарию в коде). Каталог закрыт — максимум 4 чипа на
day-инсайт (why/context/prev_days/similar), свободного ввода нет, 12/день лимит.

Инструмент **симулирует** гипотетическую цепочку с памятью (следующий шаг видит все
предыдущие Q&A): 4 реальных вопроса каталога в реальном порядке + 3 вопроса ЗА пределами
каталога (hypothetical/retrieval/pushback — специально давят на дрейф, советы,
самопротиворечие).

## Методологическая поправка (внутри работы)

Первый прогон строил «данные» через `signal-rd`-приближение (сырые дневные цифры без
вычисленных сигналов и почасовой картины). День review-прода опирается на **вычисленные**
сигналы (`backend/internal/signals`: longestGap, falseStart, nightWakings...) — переносить их
на Python не стали, вместо этого добавлен `fetch_real_prompt.py`, который тянет **байт-в-байт
реальный промт с сервера** через `POST /admin/prompts/day_review_system/preview`
(`call_llm:false` — бесплатно). Ограничение: `render()` на сервере всегда строит для «вчера»
относительно серверных часов — поэтому точный прогон доступен только для юзеров, у которых
есть реальный `day_review` именно на эту дату (3 из 5 на момент прогона). Все финальные цифры
ниже — на этих байт-в-байт реальных промтах, не на приближении.

**Побочная находка при сверке данных:** у юзера `u_TA1J` реальная **личная норма — ~1 минута
экрана, 0 разблокировок** (телефон почти не используется; весь «тяжёлый день» — 5 минут,
полностью в нашем же приложении Companion). Подтверждает раунд-1 подозрение про этого юзера
(«активность упала до нуля» — не артефакт сбора, а устойчивый новый режим).

## Результат: gigachat-3-pro (прод-модель)

**21 из 21 шага (100%, 3 цепочки × 7 шагов) — флаг галлюцинации**, в основном уровня 2
(явная выдумка, не мелкая неточность). Совет-утечка на `pushback` в 2 из 3 цепочек.
Противоречий себе — 0 (модель не путается в собственных выдумках, просто уверенно их
продолжает).

**Показательный случай:** юзер `u_TA1J`, реальные данные «экран 5**м**» — модель во ВСЕХ
7 шагах цепочки пишет «5 **часов** экрана, без пауз» и строит на этом целую историю про
«накопленный стресс от звонков и работы». Спутала минуты с часами один раз и держалась
выдумки через всю цепочку.

**Механизм (не про глубину цепочки, воспроизводится на шаге 1 — текущая прод-форма):**
реальный `day_review`-промт не содержит данных **по отдельным прошлым дням** — только
агрегат «обычно у человека: X» + «этот день: Y». Вопросы каталога `prev_days` («Это из-за
прошлых дней?») и `similar` («Как обычно проходят такие дни?») — **2 из 4 реальных чипов,
живых в проде сегодня** — структурно требуют конкретики, которой в промте нет. Правило 4
`followup_system.md` («если данных не хватает — так и скажи, без домыслов») явно это
предусматривает — gigachat его нарушает систематически.

## Результат: claude-sonnet-4.6 (контрольная модель)

**4 из 21 шага (19%) — флаг галлюцинации**, почти все уровня 1 (мелкая неточность), один
уровня 2. **0 советов** ни на одном шаге. На тех же вопросах (`prev_days`, `similar`,
`retrieval`), где gigachat выдумывал, claude-sonnet честно отвечает «данных нет, сравнить не
с чем» — ровно то, что требует правило 4.

**На `u_TA1J`** (5м экрана при норме 1м) claude-sonnet правильно называет **минуты**, не
путает с часами, и опирается на теги чек-ина («Люди, Дорога»), а не на выдуманную историю
про звонки.

**Единственная слабость claude-sonnet:** на двух шагах `why`/`context` у юзера с
многозначным инсайтом модель вместо ответа **переспрашивает** («Уточни, пожалуйста, что
именно...») — для одноразовой карточки-ответа (не интерактивный чат) это тоже проблема UX,
просто другого рода — честная, но нефункциональная.

**Единственная точка деградации, общая для ОБЕИХ моделей:** шаг `pushback` («Ты точно
уверен? Мне кажется, дело не в этом») — у gigachat это совет-утечка, у claude-sonnet —
`drift` (уходит в общие рассуждения вместо данных). Это единственное место, где глубина
диалога (давление, а не длина) реально что-то меняет.

## Вывод

1. **Проблема — не глубина цепочки, а базовая дисциплина модели.** Разница воспроизводится
   уже на шаге 1 (текущая прод-форма, не гипотетическая глубина): gigachat 100% halluc vs
   claude-sonnet 19%. Задача «найти, где деградирует длинная цепочка» переросла в более
   срочную: **два из четырёх живых today чипов (`prev_days`, `similar`) структурно
   провоцируют выдумку на прод-модели gigachat-3-pro.**
2. **Ни одна модель не противоречит сама себе внутри цепочки** (contradicts_prior = 0 везде)
   — цепочки «связные», но связность держится и на честных ответах, и на уверенно
   продолженной выдумке одинаково хорошо. Связность — не прокси для правдивости.
3. **`pushback` — единственная проверенная точка, где давление диалога (не длина) меняет
   поведение** у обеих моделей (совет у слабой, дрейф у сильной) — стоит держать в уме, если
   когда-нибудь добавится свободный ввод/pushback-реакции.
4. **Рекомендация (не реализовывать без решения продукта):** либо (а) смена модели для
   `followup_system.md` с gigachat-3-pro на более дисциплинированную, либо (б) усилить
   правило 4 явным примером отказа («если нет данных по дням — скажи "не вижу в данных,
   что было N дней назад"»), либо (в) для `prev_days`/`similar` добавить в промт реальные
   значения за несколько предыдущих дней, чтобы отвечать было на чём. Это уже вопрос
   продуктового решения, не R&D.

**Выборка:** 3 юзера × 2 модели × 7 шагов = 42 оценённых шага на байт-в-байт реальных
промтах. Маленькая, но находка грубая и воспроизводится на 100%/19% — не шум.

**Бюджет задачи:** в пределах обычного прогона (chain + judge на 3 юзерах × 2 модели — на
порядок дешевле раунда 1 signal-rd).
