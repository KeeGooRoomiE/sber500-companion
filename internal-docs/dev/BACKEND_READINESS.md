## Цепочка утреннего прогноза — где она рвётся

1. `DailyCollectWorker` раз в 12 ч шлёт снимок **сегодняшнего дня с полуночи до «сейчас»**. После полуночи строка вчерашнего дня больше не обновляется: вечер теряется.
2. Планировщик в 04:10 **по времени сервера** (Ubuntu по умолчанию UTC → 07:10 МСК) берёт пользователей, у которых есть `daily_data` **за сегодня**. Такая строка к этому моменту есть, только если телефон случайно отработал между 00:00 и 07:10.
3. «Сегодня» считается как `time.Now().Truncate(24h)` — это полночь по UTC. С 00:00 до 03:00 МСК это ещё вчерашняя дата.
4. `DailyRepo.LastN` возвращает дни от новых к старым, а `buildPrompt` считает, что от старых к новым → «сон снижается N дней» срабатывает, когда сон **растёт**.
5. Если сообщения нет, `GET /morning` отдаёт 404, и повторной попытки нет. Упал вызов LLM — пользователь до завтра без прогноза.

**Как надо:**
- приложение раз в сутки после ~03:00 отправляет **вчерашний день целиком** (плюс, как сейчас, сегодняшний частичный);
- сервер работает в явном часовом поясе (`TZ=Europe/Moscow`, дата — `time.Now().In(loc)`);
- генерация по данным «вчера + 6 дней до»;
- `GET /morning` при отсутствии сообщения генерирует его синхронно, с блокировкой на пользователя, `trigger=user_action`. Это заодно снимает вопрос Q1 к организаторам: вызов происходит в момент открытия;
- ночной батч оставить как прогрев кэша и повторить для тех, у кого была ошибка.

## Безопасность и бюджет

- **Идентификация.** Сейчас `X-User-ID = SHA256(ANDROID_ID + соль)`, соль лежит в APK. Надо: `POST /api/v1/register` → сервер выдаёт `user_id` + случайный `token`, дальше `Authorization: Bearer`. Храним только хэш токена. Без этого прогноз любого пользователя читается по его id.
- **Бюджет LLM.** Дневной лимит вызовов (`LLM_DAILY_CAP`): при превышении — локальный фолбэк и алерт в TG. Генерировать только для пользователей с данными за вчера **и** с активностью за 2 дня. Не больше одного вызова на пользователя в сутки (уже есть через `UNIQUE(user_id,date)`).
- **Лимиты запросов.** Rate limit по IP на `/register` и по пользователю на остальное (`go-chi/httprate`). `http.MaxBytesReader` на тело (64 КБ). `chi/middleware.Timeout`.
- **LLM-клиент** без таймаута: один зависший вызов стопорит весь ночной батч. `context.WithTimeout(ctx, 20*time.Second)` на вызов, 1–2 повтора с паузой.
- **Выходной текст LLM.** Проверять на ссылки и телефоны, резать по длине (есть).

## Промпты через CRUD — да, но не публичным API

Это удобно: правки тона без деплоя и A/B вариантов. Угроза реальная: утёк админ-токен → кто угодно пишет всем пользователям от имени приложения (ссылки, вредные «советы»).

Схема, которую стоит заложить:

1. Таблица `prompts(id, name, version, body, is_active, created_at, created_by, note)`. Правка создаёт **новую версию**, старые не трогаются, откат — переключить `is_active`.
2. `morning_messages.prompt_version` — видно, каким промптом сделан каждый текст. Это нужно и для метрик, и для A/B.
3. Админ-эндпоинты (`GET/POST /admin/prompts`, `POST /admin/prompts/{id}/activate`, `POST /admin/prompts/preview` — собрать промпт для user_id и, по флагу, вызвать LLM) — **на отдельном порту, слушающем только `127.0.0.1`**. Caddy его не проксирует, доступ только через `ssh -L 9090:localhost:9090 server`. Наружу не торчит вообще.
4. Плюс `ADMIN_TOKEN` (32+ байта, сравнение `subtle.ConstantTimeCompare`) — на случай, если порт когда-то откроют по ошибке.
5. Каждое изменение и активация → запись в `call_log`/аудит и сообщение в Telegram-бот «промпт morning v7 активирован».
6. Фолбэк: если активного промпта в БД нет, берётся встроенный из кода (`go:embed prompts/morning.md`) — сервер не падает на пустой таблице.

Альтернатива попроще до конкурса — промпты файлами в репе (`go:embed`) и правка через коммит + `deploy.sh`. Безопасно и с историей, но нужен деплой на каждую правку.
