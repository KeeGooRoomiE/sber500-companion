# Сигналы

Что сервер умеет замечать в данных телефона. Это единственный источник фактов для модели —
промты получают готовые сигналы и не имеют доступа к сырым числам, поэтому список сигналов
определяет потолок того, что приложение вообще способно сказать.

Код: `backend/internal/signals/signals.go`.

---

## Как устроено

```go
type Signal struct {
    Key      string   // стабильный идентификатор
    Title    string   // «Плотное утро»
    Detail   string   // «18 разблокировок до полудня — обычно 7»
    Positive bool     // окрашивает «＋» в UI
    strength float64  // насколько далеко от нормы ЧЕЛОВЕКА, не от абсолютной
}
```

`ForLastDay(days, workApps, labelOf)` берёт последний день из `days` и сравнивает его с
предыдущими. Возвращает **не больше 4** сигналов, отсортированных по `strength` — то есть по
тому, насколько день отклонился от личной нормы, а не по абсолютной величине.

Это ключевое свойство: 7 часов сна — это много или мало, зависит от того, сколько человек спит
обычно. Все пороги относительные.

`PromptBlock(signals)` рендерит их в промт. Если сигналов нет — пишет «ничего необычного, день
ровный по твоим же меркам», а не молчит.

## Многодневная цепочка

`late_night_run` — единственный сигнал **не об одном дне**.

| Ключ | Заголовок | Когда срабатывает |
|---|---|---|
| `late_night_run` | N-й вечер подряд за полночь | 2+ ночей подряд с последней разблокировкой после 00:30, и череда доходит до последнего дня |

В `Detail` добавляется, насколько сон в эти ночи короче обычного, если разница заметна.

Два правила, которые стоит помнить при правках:

- **Череда должна доходить до последнего дня.** Закончившаяся на прошлой неделе — это история, а не то, что стоит говорить сегодня утром.
- **`strength` = 2 + длина**, то есть цепочка намеренно обходит одиночные отклонения. Слотов всего четыре, и без этого её бы просто вытеснило.

Парный вопрос в «Хочу ещё» — `carries_over`, «Что тянется у меня из дня в день?». Он ищет
**самую длинную** череду за всё окно, а не только текущую: вопрос про паттерн, и прошлая
череда на него тоже отвечает. В фактах — сон и экран в эти дни против остальных, плюс ночь
после того, как череда оборвалась.

Зачем это нужно, словами интервью №20:

> «Отложить телефон после двенадцати — довольно фатальное решение, которое в силах определить
> течение последующих нескольких дней.»

Человек видит такую цепочку у себя сам, но ни одна метрика её не показывала.

## Что ограничивает список

| Ограничение | Следствие |
|---|---|
| Нет Health Connect → нет шагов | `low_move`, `active_day`, `walk`, `still_morning` не сработают |
| Нет Health Connect → нет сна | `short_sleep` / `long_sleep`, а также `morning_grab` / `calm_morning` (зависят от `wakeup`) |
| Нет доступа к истории использования | Не работает ничего: это основа |
| Мало дней истории | Личной нормы нет, сравнивать не с чем — сигналов не будет |

Последнее объясняет, почему у свежего аккаунта прогноз шаблонный: сигналов нет, и модель пишет
из общих соображений.

### Заполняемость полей — замер 2026-10-08

623 дня, 54 пользователя, окно 14 дней. Это и есть реальный охват любого сигнала,
построенного на поле.

| Поле | Заполнено | Что на нём стоит |
|---|---|---|
| `screen_min`, `unlocks`, `hourly_unlocks` | **100%** | `jumpy`, `calm_screen`, `work_load`, `morning_storm` |
| `hourly_screen` | **100%** | **ничего — поле не используется ни одним сигналом** |
| `first_unlock`, `last_unlock` | 87% | `late_phone`, `late_night_run` |
| `top_apps` | 85% | `work_load`, `calls` |
| `steps`, `hourly_steps` | 46% | `low_move`, `active_day`, `walk`, `still_morning` |
| `battery_morning` | 45% | ничего |
| `sleep_min`, `bedtime`, `wakeup` | **11%** | `short_sleep`, `long_sleep`, `morning_grab`, `calm_morning` |

**Главный вывод замера.** Health Connect починен в 0.9.9, но разрешения разделены и сон
пропускаемый — и его пропускают. Из 54 человек до экрана Health Connect дошли 25, из них
**19 выдали шаги и отказали во сне**, а сон без шагов не выдал никто. То есть потеря не в
воронке онбординга: люди доходят и осознанно отказываются именно от сна (ровно барьер из
интервью #20). Переписывать поток бессмысленно, переписывать объяснение — осмысленно.

Практическое следствие для сигналов: **четыре сигнала стоят на поле с охватом 11%.** Любой
новый сигнал на сне будет для каждого девятого, каким бы хорошим он ни был.

## В планах: сигналы из уже собираемых данных

Ничего из этого **не реализовано** — это список кандидатов. Условие отбора жёсткое: только
сырьё, которое приложение уже отправляет. Без правок Android, без новых разрешений, без
повторного consent, без изменения логики существующих сигналов — только `add(Signal{...})`.

Порядок — по охвату, а не по привлекательности идеи.

### Сначала не сигнал, а починка базы

**Норма отдельно для будней и выходных.** Сейчас `avg(base, ...)` усредняет понедельник с
воскресеньем, то есть личное «обычно» у человека — это смесь двух разных режимов.

Замер 2026-10-08: по среднему разницы нет (будни 342 мин, выходные 329), но **в разрезе
одного человека** средняя разница 33%, и у **20 из 37** пользователей с достаточной историей
будни и выходные расходятся на ≥25%. Агрегат это скрывает, потому что люди различаются в
противоположные стороны и взаимно гасятся.

Пороги срабатывания у нас 1.4× и 1.5× — ошибка нормы в треть сдвигает их заметно. Поэтому это
**улучшает все существующие сигналы сразу**, а не добавляет четырнадцатый. Охват 100%.

Тонкость: при малом числе выходных дней в истории откатываться на общую норму, иначе «обычно»
соберётся из одного воскресенья.

### Охват 100% — на `hourly_screen` и `hourly_unlocks`

| Кандидат | Что ловит | Из чего |
|---|---|---|
| `night_checks` | Разблокировки в 01:00–06:00 против обычного — «просыпался ночью и проверял телефон» | `hourly_unlocks` |
| `fragmented_day` | Сколько часов за день содержат экран: 300 минут, растянутые на 16 часов, и те же 300 за 5 часов — разные дни | `hourly_screen` |
| `long_stretch` | Самый долгий непрерывный отрезок экрана против обычного — «засиделся» | `hourly_screen` |
| `quiet_block` | Самый долгий отрезок бодрствования почти без экрана — глубокий фокус | `hourly_screen` |
| `evening_ramp` | Экран за 3 часа до последней разблокировки против нормы | `hourly_screen` + `last_unlock` |

**`night_checks` — главный кандидат.** Идея «беспокойная ночь» напрашивается на окне сна, но
сон есть у 11%. Ночные разблокировки дают почти то же наблюдение на `hourly_unlocks`, то есть
при **100%** охвата. Это в девять раз больше людей за ту же мысль.

`fragmented_day`, `long_stretch` и `quiet_block` закрывают измерение, которого у нас нет
вообще: сейчас сигналы знают **объём** экрана (`screen_min`) и **частоту** (`unlocks`), но
ничего не знают о **распределении** внутри дня.

### Поведенческие сигналы — форма дня, а не объём

Отдельный класс. Все текущие сигналы сравнивают **число** с нормой: столько-то разблокировок,
столько-то минут. Эти — про **форму**: что за чем следовало внутри дня. Такого измерения у нас
нет вообще, а человек описывает себя именно так.

| Кандидат | Паттерн | Из чего |
|---|---|---|
| `false_start` | Короткий всплеск в ранний час, потом пустой час и больше, потом настоящее начало дня | `hourly_screen` + `hourly_unlocks` |
| `no_break` | За рабочий день ни одного часа без экрана | `hourly_screen` |
| `evening_gap` | Длинный провал вечером — ушёл от телефона. Позитивный | `hourly_screen` |
| `bedtime_drift` | `last_unlock` ползёт позже несколько дней подряд — тренд, а не разовое отклонение | `last_unlock`, многодневный |
| `day_shift` | «Центр тяжести» экранного времени сдвинулся на часы против обычного | `hourly_screen` |
| `steady_rhythm` | Низкий разброс `first_unlock` за неделю — ровный ритм. Позитивный | `first_unlock`, многодневный |

**`false_start` — «будильники не помогли», без будильников и без сна.** Человек разблокировал
телефон в своё обычное время пробуждения, был активен минут пять, потом уснул снова, и день
начался позже. Весь паттерн виден в почасовых данных: всплеск, провал, настоящее начало.

Тонкость реализации: часовые корзины грубые. Всплеск в 06:55 и реальное начало в 07:05 попадут
в соседние корзины и неотличимы от обычного пробуждения. Поэтому провал должен быть **минимум
один полный пустой час**, иначе сигнал будет врать.

`evening_gap` и `steady_rhythm` стоит отметить отдельно: позитивных сигналов у нас мало
(`calm_morning`, `calm_screen`, `walk`, `active_day`, `long_sleep`), а два из пяти стоят на сне
и шагах. То есть человеку без Health Connect почти нечего сказать хорошего — а это тот самый
риск «самобичевания» из интервью #16.

### Длина сессии — метрика, которой у нас нет

`screen_min / unlocks` — это средняя длина сессии, и она информативнее обоих чисел по
отдельности. Сейчас мы её не считаем.

Исследования дают этому опору (подробно с источниками — [RESEARCH_USAGE.md](RESEARCH_USAGE.md)).
Oulasvirta и соавторы (2012) описали «checking habits» —
короткие повторяющиеся заглядывания в телефон, и отдельно отметили, что сами люди переживают
их как раздражающую помеху, а не как зависимость. Jones и Gonçalves (UbiComp 2015) построили
типологию по паттерну возвратов и выделили «Checkers» — 44% выборки, у них возвраты резко
смещены в сторону коротких. Средняя сессия приложения там около 72 секунд.

Практический вывод: **одно и то же число разблокировок означает противоположные вещи при
разной длине сессии.**

| Кандидат | Что ловит | Почему важно |
|---|---|---|
| `checking_day` | Сессии заметно короче обычного при том же или большем числе разблокировок | Это и есть «дёрганый день» в правильной формулировке. Текущий `jumpy` смотрит только на счётчик и не отличает тридцать заглядываний по минуте от тридцати осмысленных заходов |
| `immersed_day` | Сессии заметно длиннее обычного | Долгие посадки. Отдельный режим, который сейчас невидим: человек может не блокировать экран часами, и `unlocks` у него будет низким, как у спокойного дня |

Оба на 100% охвата, оба из полей, которые уже есть.

### Неоднозначные сигналы должны становиться вопросами, а не утверждениями

Телефон физически не различает ряд противоположных ситуаций:

- **Мало экрана в выходной** — гулял весь день или просидел десять часов за компьютером
- **Мало разблокировок днём** — сосредоточенная работа или просто не трогал телефон
- **Много экрана** — залипал или вёл навигацию / слушал аудиокнигу

Последнее подтверждается жалобами пользователей на штатные счётчики: музыка, карты,
аудиокниги и подкасты попадают в экранное время, и люди считают свои цифры «ненастоящими».

Правило для таких случаев: **не утверждать, а спрашивать.** Механизм уже есть — «Вопрос дня»
вышел в 1.0.0, follow-up чипы в 0.9.9. То есть неоднозначный сигнал не выбрасывается, а
превращается в вопрос с вариантами ответа, а ответ уходит в профиль и снимает неоднозначность
на будущее.

Это дешевле, чем новые данные, и честнее, чем угадывать.

### Шаги как дизамбигуатор

Там, где шаги есть (46%), они разрешают неоднозначность, которую экран не разрешает:

| Экран | Шаги | Трактовка |
|---|---|---|
| Мало | Много | Был на ногах — телефон не понадобился |
| Мало | Мало | Сидячий день без телефона: компьютер, телевизор, книга |
| Много | Много | Телефон в движении — дорога, навигация |
| Много | Мало | Сидячее залипание |

Ни один из четырёх выводов не получить из одного источника. Это аргумент за то, чтобы
комбинированные сигналы считались до того, как браться за новые источники данных.

### Белые списки приложений: расширить, но честно

Запрос «открывал приложение для сна вечером» и «фитнес утром» упирается в то же ограничение,
что и видео: категорий приложений у нас нет. Но механизм белого списка уже работает для работы
(`knownWorkApps`) и звонков (`callApps`), и его можно расширить ещё на пару категорий, где
список коротких и узнаваемых пакетов реально покрывает большинство случаев.

Оговорка, которую надо держать в голове: это **не категоризация**, а ручной список. Он будет
неполным, и для широких категорий вроде видео — заведомо неполным настолько, что сигнал начнёт
врать. Для узких (приложения сна, трекеры тренировок) покрытие приличное.

Чего всё равно нельзя: сказать, что приложение работало **в фоне**. UsageStats считает
передний план. Если приложение сна включили и погасили экран, минут в `top_apps` почти не
будет.

### Чего на экранном времени сделать нельзя

**Нет разбивки приложений по часам.** `top_apps` — это суточные итоги (package + minutes),
`hourly_screen` — суммарные минуты в часе. Связи между ними нет.

Поэтому невозможно: «что именно он смотрел вечером», «соцсети после полуночи», «работа после
20:00», «засиделся в видео». Любой сигнал вида «какое приложение в какой час» требует новых
сырых данных с устройства.

Это же ограничивает и запрос на детальную раскладку экранного времени в приложении: показать
можно либо топ приложений за день, либо почасовой график общего экрана, но не пересечение.

### Охват 85–87% — `first_unlock`, `top_apps`

| Кандидат | Что ловит | Из чего |
|---|---|---|
| `late_start` | Первая разблокировка позже обычного — день начался со сдвигом | `first_unlock` |
| `start_jitter` | Разброс времени первой разблокировки за неделю — нерегулярный подъём | `first_unlock`, многодневный |
| `new_app` | В топе дня приложение, которого обычно там нет, с заметными минутами | `top_apps` |
| `one_app_day` | Доля самого верхнего приложения в экранном времени — день, съеденный одним приложением | `top_apps` |

`late_start` и `start_jitter` стоит отметить отдельно: `morning_grab` и `calm_morning` делают
близкие наблюдения, но через `wakeup` — охват 11%. Те же мысли на `first_unlock` работают при
87%.

`new_app` и `one_app_day` интересны тем, что вся текущая работа с приложениями — это два
белых списка (`knownWorkApps`, `callApps`). Сравнение топа с собственной историей — другой
принцип, и ему не нужны ни категории, ни списки.

### Охват 45% — низкий приоритет

`charged_overnight` на `battery_morning`: уровень заряда утром как прокси стабильности
вечерней рутины.

### Что из обсуждавшегося сделать нельзя

| Идея | Почему нет |
|---|---|
| «Будильники не помогли» в буквальном виде | Данных о будильниках нет и не будет без нового разрешения. **Но поведенческая версия возможна** — см. `false_start` выше: всплеск, провал, позднее начало дня. Самих будильников для этого не нужно |
| «Засиделся в видео» | У нас `package` и `minutes`, категорий приложений нет. Можно только ещё один белый список вручную — это не категоризация, и для видео он будет заведомо неполным |
| Качество сна, стадии, пульс | Требует расширения скоупов Health Connect, а сон уже отказывают 76% дошедших |

### Мок-персоны: почему их придётся переделать первыми

Почасовые массивы персон **не авторские, а производные**: `gen_personas.py` раскладывает
дневной итог между `first_unlock` и `last_unlock` функцией `hourly()`, а экран выводит из
разблокировок через `screen_hourly()`. Получается гладкое распределение без провалов.

Следствие: **ни одна из шести текущих персон не может воспроизвести ни один поведенческий
сигнал.** «Проснулся и уснул снова» требует дырки в середине утра, которой генератор не
создаёт в принципе. То же для `evening_gap`, `no_break`, `quiet_block`, `fragmented_day`.

Значит порядок работ такой: **сначала персоны, потом сигналы.** Иначе проверять будет не на
чем — останутся только юнит-тесты на синтетических массивах, а прогон `eval --llm` по персонам,
которым мы доверяем качество промптов, новые сигналы просто не затронет.

Что нужно:

1. Разрешить в `gen_personas.py` задавать `hourly_screen` / `hourly_unlocks` явно, а не только
   выводить из итогов — авторский массив там, где важна форма дня
2. Добавить персон под новые паттерны: ложное пробуждение, день без перерывов, вечер без
   телефона, рваный день против собранного
3. Обновить `mock_test_data_week.json` — там неделя, на которой удобно проверять многодневные
   `bedtime_drift` и `steady_rhythm`
4. `mock_test.go` уже проверяет длину 24 — добавить проверку, что у персон с авторской формой
   она не затёрлась генератором

Персоны — это ещё и то, на чём гоняется `eval --llm` при правках промптов. Поэтому их качество
влияет не только на тесты сигналов.

## Инсайты (`POST /api/v1/insight`)

Один механизм, пять срезов. Отличаются только фактами на входе и задачей; кэш, бюджет и
логирование — общие. Кэш — по `(user, kind, arg, день)`, ключ ревью `in:<kind>[:<arg>]`,
дневной лимит `InsightDailyLimit = 50` (считается по префиксу `in:`).

| kind | arg | Где в приложении | Когда вызывается |
|------|-----|------------------|------------------|
| `midday` | — | «Как идёт день» — второй раздел внутри карточки прогноза (не отдельная карточка, см. ниже) | открытие Home в 12:00–18:00, после доотправки данных за сегодня |
| `stat` | `screen` \| `sleep` \| `unlocks` | строка «Что это значит» в шите плитки | тап по плитке |
| `retro` | `YYYY-MM-DD` | строка «Как вышло» внутри панели «Прошлые прогнозы» | раскрытие панели |
| `tag` | текст метки | строка под свёрнутым чек-ином | после отправки чек-ина, по первой метке |
| `question` | `1`..`3` (слот дня) | карточка перед «Когда присылать прогноз» в «Расскажи о себе» + баннер над прогнозом на Home (слот `1`, лимит 1/день) | открытие профиля / Home; следующий слот запрашивается только после ответа на текущий |
| `profile` | `1` (база) / `2` (после уточнения) | «Твой профиль» — карточка сразу после «какие приложения рабочие» в «Расскажи о себе» | открытие профиля (`1`, кэш на день); `2` — только сразу после ответа на `profile_clarify` |
| `profile_clarify` | — | вопрос+варианты под «Твой профиль», кнопка «Уточнить» | тап «Уточнить», 1 раз в день (`AppPrefs.wasProfileClarifiedToday`) |
| `orbtap` | `1`..`5` (слот дня) | пузырь-реакция над орбом | 3 тапа по орбу за 5 сек (флёрри); следующий слот — только после следующего флёрри |

Отказы молчаливые: `404` (мало данных), `429` (лимит), ошибка сети — строка просто не
появляется. Экраны, куда они встроены, осмысленны и без них.

### Ответы на сгенерированные вопросы

Ключ вопроса — хэш его текста (`gen_<base36>`), потому что до генерации вопроса не существует и
в allowlist его быть не может: сервер проверяет форму ключа (`gen_`, ≤64 символа) и хранит не
больше `maxGenAnswers = 20`. Сам текст вопроса сервер прочитать не может, поэтому он уезжает
внутрь значения — `«вопрос» — ответ`. На телефоне текст лежит рядом под `genq_<base36>` (локальный
префикс, на сервер не уходит), чтобы отвеченная карточка могла отрисоваться.
В промпт ответы попадают через `profileContext` (`internal/llm/morning.go`) как отдельные строки
блока «Контекст о человеке».


### Слоты `question` (до 3 в день)

До правки `question` кэшировался одним слотом на день (`in:question`) — максимум 1 вызов в
день независимо от того, сколько раз открыт профиль. Теперь слотов три (`in:question:1..3`),
но клиент продвигается на следующий **только после ответа** на текущий ([ProfileViewModel.kt](../../android/app/src/main/kotlin/ru/keegoo/companion/ui/profile/ProfileViewModel.kt)
`onGeneratedAnswered()`), а не при каждом открытии экрана. День без ответа — ровно один вызов,
как раньше; вовлечённый день — до трёх. Счётчик слота живёт в `AppPrefs` (`gen_question_slot`),
сбрасывается по дате.

При текущем `llm.MaxGenAnswers = 20` и кадансе до 3/день профиль может достичь потолка хранения
за ~7 дней активного использования вместо ~20 — после этого генерация `question` для человека
прекращается (см. гейт в `insightPrompt`), пока число отвеченных `gen_`-ответов не станет < 20.


### Формат ответа `question`: вопрос + варианты

Системный промпт (`internal/llm/prompts/insight_system.md`) просит у модели две строки:
вопрос, затем `Варианты: А | Б[ | В]`. На практике модель (gigachat-3-pro) почти всегда кладёт
всё в одну строку — проверено на 20 реальных вызовах. `forecast.ParseQuestionAnswer`
([insight.go](../../backend/internal/forecast/insight.go)) это не требует: ищет «Варианты» где
угодно в тексте, иначе — двоеточие с `|`-списком после него, иначе — классический двустрочный
вид. Срезает случайное вступление перед вопросом (`lastSentence`) и `?`/`.` в конце последнего
варианта. Сырой текст кэшируется как есть; разбор — только при формировании ответа
(`internal/api/insight.go`), только для `kind=question`. Если ничего не нашлось или вариант
один — `options` пустой, клиент показывает вопрос как свободный текст.

**Баг с реального пользователя (2026-10-03):** вопрос заканчивался двоеточием вместо «?», а
варианты повторялись внутри текста вопроса («Ты дома или в офисе? Варианты: Дома | В офисе») —
чипы визуально дублировали то, что уже было в самом вопросе. Правка в двух местах:
1. Системный промпт — явно запрещено называть варианты внутри вопроса («не пиши ...А или Б?»),
   с примером плохо/хорошо; задачи `InsightQuestion`/`InsightProfileClarify` получили то же
   напоминание.
2. Защита в парсере — `questionRepeatsOptions`: если все варианты уже встречаются в тексте
   вопроса (регистронезависимо), чипы отбрасываются, остаётся чистый вопрос без вариантов.
   На живом прогоне после правки промпта модель всё равно давала дубль в 4 из 15 случаев —
   защита в парсере сработала во всех четырёх и показала чистый вопрос без дублей.

**Второй баг с реального пользователя (2026-10-03, тот же день):** `midday` на главном экране
показал сырой текст с дописанным в конце вопросом и вариантами — «...почти 3 часа против 41
минуты.\n\nВ чём ты сегодня больше всего отвлекался: в рабочих чатах или на случайные
приложения?\nВарианты: Рабочие чаты | Случайные приложения». У `midday` (как и у `stat`/`retro`/
`tag`/`profile`) нет вообще никакого разбора — текст уходит клиенту как есть, так что утечка
показывается дословно, co словом «Варианты» внутри карточки. Модель решила дописать вопрос,
которого никто не просил (видимо, паттерн самого формата «вопрос+варианты» из этого же system
prompt иногда всплывает там, где не должен). Правка:
1. Системный промпт — отдельное правило 9: «никогда не дописывай вопрос с вариантами, если не
   в разделе "задать вопрос"»; дефолтный формат явно ограничен одним абзацем.
2. `forecast.StripLeakedQuestion` — применяется при отдаче ответа (`internal/api/insight.go`)
   **ко всем kind, кроме `question`/`profile_clarify`** (у `orbtap` уже есть своя защита через
   `SafeOrbReaction` — утёкший хвост не кончается на `.!?…`, тот же эффект). Режет по первому
   вхождению «варианты» (без учёта регистра), а если метки нет вообще — по последнему абзацу,
   если это отдельное предложение с «?» на конце. Работает на **уже закэшированном** тексте —
   так как разбор идёт при отдаче, а не при генерации, сломанная карточка из бага выше
   самовылечится на следующий же запрос, без ожидания сброса кэша по дате.
   На живом прогоне после правки промпта (18 вызовов, `stat`+`profile`) — утечек 0/18.

**UX-последствие того же дня:** после фикса парсинга карточка `midday` осталась голым абзацем
текста без чипов и без кнопки — на фоне яркой карточки прогноза (кнопка, заливка) и цветных
плиток ниже это читалось как «информационное нагромождение» (отзыв пользователя). Решение —
не отдельная карточка, а **второй раздел внутри карточки прогноза** (`MorningCard` в
`HomeScreen.kt`): «Прогноз на сегодня» → текст → «Как идёт день» → текст → «Почему такой
прогноз ▾» → кнопка (переименована «Спросить о себе» → «Узнать больше»). `MiddayCard` как
отдельный компонент удалён из `HomeInsight.kt`, `HomeBlock.Midday` убран из enum — `midday`
больше не отдельный элемент `LazyColumn`, просто поле, которое `MorningCard` получает и рисует
сама. Вызов/кэш/лимит (1/день, окно 12–18ч) не менялись — поменялась только презентация.


### «Твой профиль» + «Уточнить» (идея 2)

Базовый вызов (`profile`, слот `1`) — описание человека на основе данных + `KnownProfileFacts`,
кэш на день, как у остальных инсайтов: без вовлечения — ровно 1 вызов/день за фичу.

«Уточнить» — второй, отдельный вызов (`profile_clarify`), который видит текст слота `1`
(читает кэш `in:profile:1` напрямую через `g.reviews.Get`, а не параметром) и генерирует
вопрос+варианты в том же формате, что и `question`/`ParseQuestionAnswer`. Ответ сохраняется как
обычный `gen_`-факт (то же `genQuestionId`/`GenQuestionTextPrefix`, что у generated questions) —
это заставляет его попасть в `KnownProfileFacts` при следующей генерации. Клиент отправляет
профиль на сервер **синхронно** перед запросом слота `2` ([ProfileViewModel.kt](../../android/app/src/main/kotlin/ru/keegoo/companion/ui/profile/ProfileViewModel.kt)
`answerClarify`) — иначе был бы race с debounce-синком `HomeViewModel.syncProfile` (1 сек), и
слот `2` сгенерировался бы без нового факта.

«Уточнить» доступен 1 раз в день (`AppPrefs.wasProfileClarifiedToday`/`markProfileClarified`).
Итого по фиче: пассивный день — 1 вызов (`profile:1`), вовлечённый — до 3 (`profile:1` +
`profile_clarify` + `profile:2`).

Композиция ответов в формат сервера (`«вопрос» — ответ` для `gen_`-ключей) вынесена в одну
функцию — `composeProfileForServer` ([ProfileQuestions.kt](../../android/app/src/main/kotlin/ru/keegoo/companion/domain/profile/ProfileQuestions.kt)),
используется и `HomeViewModel.syncProfile`, и `ProfileViewModel.answerClarify`.


### Орб: тапы, самопульс, пузырь-реакция (гипотеза «взаимодействие с орбом»)

**Только на большом орбе в «Расскажи о себе»** (`ProfileScreen.kt`) — на маленьком орбе в
`TopBar` (Home) этой механики нет вообще, там обычный тап открывает профиль без каких-либо
жестов/анимаций сверх тех, что были раньше. Решение сознательное: разводить тап-навигацию и
тап-флёрри на одной маленькой иконке оказалось лишним, когда есть отдельный большой орб именно
для этого взаимодействия.

Семь независимых механик на одном экране:

1. **Дизамбигуация тапа** (`ui/motion/OrbGesture.kt`, `rememberOrbGesture`): три тапа за 5 секунд
   — флёрри, идёт реакция. Одиночный тап на этом экране ничего не открывает (мы уже здесь) —
   `onSingle` пустой. `onTap` (сквиш + хаптик) срабатывает на каждый тап независимо от исхода.
2. **Самопульс**: раз в случайные 6–9 секунд, пока экран открыт, орб слегка увеличивается —
   бесплатно, визуально, без вызова.
3. **Инвайт через 9 секунд**: если за 9 секунд ни одного тапа не было, один раз показывается
   фраза-приглашение из `OrbInvitePool` (статика, без вызова) — и через 3.5 секунды сама
   исчезает (баг первой версии: не было таймера на скрытие, облако висело бесконечно).
   Сбрасывается первым тапом.
4. **Пузырь-реакция на флёрри** (`ProfileViewModel.onOrbFlurry`, через общий
   `ui/motion/resolveOrbReaction`): 5 слотов в день
   (`AppPrefs.orbTapSlotToday`/`advanceOrbTapSlot`, сбрасываются по дате), каждый привязан к
   своему факту на бэке — не 5 одинаковых вопросов подряд:
   - слот 1 → экран (сегодня/обычно)
   - слот 2 → сон
   - слот 3 → разблокировки
   - слот 4 → первый сигнал дня (`signals.ForLastDay`)
   - слот 5 → тег чек-ина за сегодня, если уже отмечен, иначе топ-приложение последнего дня

   Слот продвигается **только после флёрри**, успешного или нет — исчерпание 5 слотов или сбой
   вызова даёт случайную фразу из `OrbReactionPool` (те же формулировки, что в исходной
   гипотезе: «Тебе скучно?», «Хочешь поговорить?» и т.д.), без обращения к сети.

   Лимит символов жёстче всех остальных инсайтов — `OrbTapLimits = {Tokens: 30, Chars: 60}`:
   пузырь висит на экране ~1 секунду, обрыв слова посередине читается как баг. `SafeOrbReaction`
   (`internal/forecast/insight.go`) проверяет, что текст оканчивается на `.`/`!`/`?`/`…`; если
   60-символьный лимит обрубил фразу без знака в конце — сервер отвечает 404 «not enough data»,
   клиент показывает статичную фразу вместо обрывка. На живом прогоне (30 вызовов, 6 персон × 5
   слотов) — 1/30 случаев дал обрыв и корректно упал на фоллбэк.

5. **Ускорение анимации на тап и на реакцию** (`CompanionOrb(speed = ...)`): дыхание/блик/wobble
   — всё, что приводится в движение временем `t` в `Canvas` — управляется снаружи через
   `speed: Float` (раньше было `reacting: Boolean` с зашитым внутри 2.2×; теперь вызывающая
   сторона сама ведёт `Animatable`). `ProfileScreen` держит `morphSpeed`: на каждый тап —
   мгновенный скачок до 3× и спад за 240 мс (было 550 мс — укорочено вдвое по отзыву: «весь
   цикл должен быть быстрее»); пока висит пузырь-реакции — держится на 3×, затем спадает за те
   же 240 мс.

   Рядом — `wobbleBoost: Float`, отдельная ручка на саму амплитуду «капли в невесомости» (три
   синус-слагаемых формы блоба в `Canvas`, каждое домножается на `wobbleBoost`). На тап —
   скачок до 1.18× за 90 мс, спад до 1× за 260 мс: орб не просто быстрее дышит (`speed`), он
   ещё и чуть сильнее «расползается» в стороны — как будто его сжали и отпустили.

   Сквиш (`orbScale`) сделан заметно слабее и быстрее: было падение до 0.82 с полным циклом
   norm→shrink→norm около 900 мс (пружина с низким демпфированием долго доходила до покоя,
   плюс амплитуда слишком сильно меняла пропорции), стало — падение до 0.93 за 50 мс и пружина
   назад с `dampingRatio=0.7, stiffness=500` — полный цикл укладывается в ~0.25 с.

   Рипл с тапа убран (`indication = null`) — у орба уже есть свои волны (п.6), серая обводка
   поверх них визуально мешала.
6. **Волны от тапа, два вида** (`CompanionOrb`, список `waves` — `Float`, момент `t` на спавне):
   каждый тап увеличивает `waveTrigger`, что добавляет новую волну (старые, кому вышел срок,
   чистятся тут же). На каждую волну рисуются одновременно:
   - тонкое кольцо — мгновенный отклик, растёт `r → r×1.35` за 0.28 с, альфа линейно до 0;
   - прозрачная заливка — догоняет с задержкой 0.12 с, растёт до `r×2` за 0.7 с, альфа всего
     ~6%, но затухание квадратичное от прогресса (`(1-p)²`) — держится почти не тусклой, пока
     маленькая, и резко гаснет к концу роста, а не линейно по времени.
   Несколько тапов подряд (флёрри) кладут волны друг на друга слоями — не одна и та же волна
   перезапускается, а появляется новая поверх ещё не угасшей.
7. **Сворачивание в тулбар при скролле** (аналог аватарки в Телеграме): орб вынесен из
   `LazyColumn` в отдельный floating-оверлей над списком. При скролле вниз орб уменьшается с
   104dp до 28dp и едет **в зону статус-бара** (`collapsedCenterY = bars.calculateTopPadding() / 2`)
   — не просто в полосу с кнопкой «назад» пониже (первая версия ошибочно останавливала его там;
   сама полоса с кнопкой осталась на месте, 56dp, и набирает фон по мере сворачивания, но орб
   едет выше неё, туда же, где реальный вырез камеры). При скролле назад — возвращается.
   Пузырь-реакция/инвайт прячется после 60% сворачивания. Место орба в `LazyColumn` держит
   `Spacer(ORB_SLOT_HEIGHT)`, чтобы текст ниже не прыгал. Цитата над орбом поднята на 1.5 своей
   измеренной высоты (`onSizeChanged`, не константа — одна строка и две строки текста
   поднимаются на разную высоту корректно).

   **Переход — не линейная привязка к скроллу, а флип + анимация.** Первая версия тянула
   размер/позицию орба 1:1 за пальцем — из-за этого было видно «промежуточное» состояние на
   полпути, которого не должно быть. Теперь `orbCollapsed: Boolean` переключается по двум
   разным порогам с гистерезисом (`ORB_COLLAPSE_AT = 24dp` / `ORB_EXPAND_AT = 6dp` — было
   110dp/20dp, укорочено по отзыву «реагирует на минимальный скролл», через `snapshotFlow` на
   `listState`, не `derivedStateOf` — нужно «помнить» предыдущее состояние внутри мёртвой зоны
   между порогами) — скролл только решает, в каком он состоянии, а не рисует его напрямую.
   Сама анимация — отдельный `Animatable`, не завязанный на скролл: сворачивание —
   `tween(320, OrbDockEasing)`, где `OrbDockEasing = CubicBezierEasing(0.25, 0.1, 0.25, 1)` —
   это ровно CSS-дефолтный `ease` (было `FastOutLinearInEasing`, попросили «капля вливается»,
   не механический линейный слайд); разворачивание — `spring(dampingRatio = MediumBouncy)` (с
   лёгким перелётом, «капля приземлилась»). Перелёт пружины может дать `collapseProgress` чуть
   за пределы `0f..1f` — это намеренно для эффекта разворота; альфа фона бара отдельно зажата в
   `coerceIn(0f, 1f)`, чтобы не словить отрицательный alpha у цвета.

8. **Затемнение и исчезновение у самой камеры — две стадии, не одна.** Первая версия тянула
   доуменьшение прямо внутри той же интерполяции, что цвет и размер до «размера камеры» — по
   отзыву это читалось как «улетает в бесконечность», а не как «доехал, встал, растворился».
   Теперь это буквально две последовательные `Animatable`, запускаемые строго по очереди в
   одном `LaunchedEffect(orbCollapsed)` — вторая физически не может начаться, пока первая не
   доанимировалась (suspend-вызовы в одной корутине):
   - `dockAnim` (стадия 1) — доезд до позиции камеры, уменьшение `104dp → 28dp`.
   - `hideAnim` (стадия 2) — запускается **только после** `dockAnim.animateTo(1f, ...)` —
     доуменьшает уже стоящий кружок (ещё на 92% от его текущего размера) и гасит по альфе до
     0 — «чёрная рамка вокруг камеры просто стала меньше», как Dynamic Island.
   - Обратно — тоже строго по очереди, но в обратном порядке: сначала `hideAnim` обратно к 0
     (появление из ничего в размере камеры), и только потом `dockAnim` обратно к 0 (доезд +
     рост до полного размера). Направление не требует отдельной логики — та же пара анимаций
     просто проигрывается в обратную сторону.
   - Блик на поверхности (`Color.White` в радиальном градиенте тела) тоже блендится в чёрный
     через `blackout` — без этого на `blackout=1` орб выглядел бы как «чёрный шар с бликом»,
     не как сплошная чёрная точка (дословный отзыв: «не чёрного цвета с отблеском»).

   **Цвет — отдельная анимация, не функция от `dockAnim`.** Было: `blackout` считался прямо из
   `dockAnim`'s прогресса по порогу (последние 20% пути). Проблема вскрылась на развороте:
   обратный `dockAnim` — пружина, нелинейная, медленно стартует — и почернение/расчернение,
   завязанное на неё, визуально «не поспевало» за остальной анимацией (дословно из отзыва).
   Завели третий `Animatable` — `blackoutAnim` — с собственным `tween` в каждую сторону,
   независимым от того, что делает пружина:
   - сворачивание: `tween(90, delayMillis = 230)` — успевает к чёрному ровно к концу 320мс
     доезда, запущен как параллельный `launch { }` внутри `LaunchedEffect`, не блокируя
     последовательность `dockAnim → hideAnim`;
   - разворот: `tween(160)`, тоже `launch { }`, стартует сразу после `hideAnim` вернулась к 0
     — расчернение заведомо быстрее, чем обычно успевает устояться пружина роста (та обычно
     занимает 300-400мс+), так что цвет «обгоняет» рост, а не отстаёт от него.

   **Длительности сокращены по отзыву** («чёрный держится долго», «появление еле поспевает»):
   - `hideAnim` вперёд (прятка): 240мс → 120мс (вдвое).
   - `hideAnim` назад (появление из ничего): 200мс → 50мс (вчетверо) — почти мгновенно, чтобы
     рост начинался сразу, как орб «появился».
   - `dockAnim` (сам доезд/рост) не трогал — жалоба была явно не про «когда он летит».

   **Волны-от-тапа гейтятся по размеру** (`CompanionOrb(sizeFraction = ...)`): волны (п.6)
   рисуются только пока `sizeFraction = stage1Size / ORB_EXPANDED_SIZE >= 0.7` — иначе было
   видно, как они продолжают расходиться на уже сжавшемся/чёрном кружке у камеры, что не
   читалось как «живой» эффект.

   Геометрия (длительности, цвет-бленд, порог волн) выверена на бумаге, не на экране — нужна
   проверка на устройстве.

### Плейсхолдер в поле свободного ответа

`FreeTextAnswer` — общий компонент для ВСЕХ freeText-вопросов (`ProfileQuestions.kt`): и
фиксированного «Как к тебе обращаться?», и любого сгенерированного вопроса без вариантов
(`question`-инсайт без `options`). Плейсхолдер `"Например, Саша"` был зашит один на всех —
для имени уместно, для случайного сгенерированного вопроса («Как ты обычно ощущаешь себя после
работы в офисе?») — нет. Добавил `ProfileQuestion.freeTextPlaceholder: String?` (null = общий
`"Написать..."`), у NAME — явно `"Например, Саша"`.

Отдельно проверил на бэкенде (`ParseQuestionAnswer`) оба примера из отзыва — оба парсятся
корректно текущим кодом (второй, с `|`-списком в тексте, верно разбивается на 3 чипа). То, что
пользователь видел сырой текст, скорее всего — старый кэш/билд до фикса парсера, а не новая дыра.
