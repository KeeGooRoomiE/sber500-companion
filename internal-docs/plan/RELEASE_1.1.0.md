# Релиз-кандидат 1.1.0 — что копим

Собираем **одним релизом**, тег не ставим до сборки. Причина: модерация RuStore стоит
одинаково для одной правки и для десяти, а каждый отдельный цикл съедает дни из зачётного
периода (5.11 — 2.12). Версия в сторе и версия бэкенда синхронизируются в один день из
артефакта CI: владелец скачивает APK и подаёт в консоль вручную.

Ничего из списка ниже пока не написано — это план.

---

## Почему вообще нужен релиз

Метрика «обращений на 1 DAU» считается **среднесуточно за весь период**. На 09.11 прожито
5 дней со средним 4.3, то есть в банке 21.5 из нужных 280. Оставшиеся 23 дня должны идти
по 11.2 — подъём в 2.6 раза.

Главное, что показали данные 09.11: **4.3 — это среднее двух разных популяций.**

| Вызовов за день | Человек |
|---|---|
| 1 | **173** |
| 2–5 | 91 |
| 6–10 | 122 |
| 11+ | 24 |

173 человека из 410 сделали ровно один вызов — им пришёл утренний прогноз, и приложение
они не открыли. При этом 146 человек уже делают шесть и больше. **Потолок упирается не в
архитектуру, а в то, что сорок два процента не заходят.** Для них единственный канал —
уведомление, а уведомления планируются на устройстве. Отсюда и необходимость релиза.

Охват механик за 7 дней (людей): утро 523, инсайт 481, разбор дня 356, недельная 217,
follow-up 99, «Хочу ещё» 86.

## Что входит

### 1. Дневной пуш около 14:00 — главный

Один LLM-вызов и новая точка входа в середине дня: «половина дня прошла, вот что заметно».

Единственная механика, которая достаёт тех самых 173 молчунов: они не открывают приложение,
и только уведомление до них доходит. Остальные идеи работают с теми, кто и так заходит.

Планировать тем же `AlarmManager`, что утренний прогноз, с теми же предохранителями:
следующий будильник взводится до сетевой работы, бюджет на запрос текста ограничен.

### 2. Ответ на утренний прогноз прямо из шторки

Кнопка «Совпало / Не совсем» уже есть, а вот уточняющий вопрос — нет. Тап из уведомления
должен открывать follow-up без захода в приложение.

Follow-up не сломан: у тех 99, кто до него добирается, по 2.2 вызова. Сломано обнаружение —
81% активных его не находят. Перенос точки входа в уведомление лечит именно это.

### 3. Обновление существующих уведомлений — дёшево, делаем заодно

Вечерний чек-ин и разбор дня уже ходят через `AlarmManager`. Если дневной пуш всё равно
добавляется, стоит пересмотреть тексты всех трёх: по данным 05.11 напоминание в 20:30 даёт
только 17% отметок в течение часа, 42% приходят после 21:30.

### 4. Серверные пуши — вернуть возможность будить приложение

Сейчас сервер не может достучаться до телефона вообще: FCM удалён при подготовке к RuStore,
все уведомления планируются на устройстве через `AlarmManager`. Это значит, что любой новый
повод открыть приложение требует релиза и ждёт модерацию, а никакой срочной рассылки —
«вышла новая версия», «посмотри итоги недели», реактивация уснувших — сделать нельзя.

**Что выяснилось по документации (09.11).**

У AppMetrica есть серверный Push API: `POST https://push.api.appmetrica.yandex.net/push/v1/send-batch`,
авторизация заголовком `Authorization: OAuth <токен>`, свои заголовок и текст, диплинк,
до 250 000 устройств за запрос, сообщение до 3968 байт. Отчёты по доставке и открытиям
(`ym:pc:openedDevices`, `ym:pc:conversion`) идут из коробки.

**Процента аудитории в API нет** — получатели задаются явными списками устройств
(`appmetrica_device_id`, `android_push_token` и другие). Это не мешает: выборку делаем у
себя, и «те, кто получил прогноз и ни разу не открыл приложение» точнее любого случайного
процента. В веб-интерфейсе есть стандартные сегменты и A/B на четыре гипотезы с контрольной
группой.

**Нерешённое, выяснить до начала работы.** У AppMetrica Push есть провайдер
`provider-rustore` (`ru.rustore.sdk:pushclient`), а `provider-firebase` исключается из
сборки. Но в `send-batch` **нет типа идентификатора для RuStore**, а в описании
`time_to_live` упоминается FireBase. То есть доставка по RuStore-токену через этот API
документацией не подтверждена. Решается вопросом в поддержку или одной тестовой отправкой.
Если не поддерживается — берём RuStore Push напрямую, но теряем готовые отчёты по открытиям.

**Проверить также**, не добавляет ли push-SDK чувствительных разрешений: если добавляет,
публикация через Public API отвалится с 400 и потребует ручной декларации в консоли
(см. «Чего в релизе делать нельзя»).

**Сколько работы.** От FCM-времён не осталось ничего: в бэкенде кода отправки нет, миграция
`004_device_tokens` — про токены авторизации, а не пуши. Выжило мёртвое поле `fcm_token` в
Android-DTO, которое никогда не заполняется. Делать с нуля: получение токена в приложении,
хранение у нас, эндпоинт адресной рассылки, журналирование в `call_log` с
`trigger=scheduled`, чтобы фоновые отправки не смешались с инициированными человеком.

### 5. Конверсия аудитории — онбординг

По данным 05.11 двадцать четыре человека из пятидесяти четырёх зарегистрировались и не
прислали даже версию приложения, то есть **до главного экрана не дошли сорок четыре
процента**. Онбординг просит пять разрешений подряд до первой полезной фразы, а третий шаг
выбрасывает в системные настройки.

Ответ уже нарисован: прототип с проявляющимися цифрами —
[companion-app.ru/onboarding-reveal](https://companion-app.ru/onboarding-reveal/). Ценность
показывается по мере выдачи разрешений, а не после пятого «Разрешить».

Это самая дорогая позиция в списке по работе и самая дорогая по цене бездействия: при CPI
около 120 ₽ каждый непрошедший онбординг — оплаченный клик, который не стал пользователем.

### 6. Связь с автором — инструмент кастдева, а не ссылка в настройках

Формулировка ментора: встроить так, чтобы получать кастдев **с уже существующих
незаинтересованных пользователей**. Это меняет и приоритет, и дизайн.

**Зачем.** Все 27 интервью проведены с тёплыми, которых владелец приводил сам. По холодному
платному трафику, который теперь составляет большинство, качественных данных ноль. Мы знаем,
что 173 человека из 410 делают ровно один вызов в день и что 44% не доходят до главного
экрана, но не знаем **ни одной причины** — только цифры. Без этого любая правка онбординга
и механик делается вслепую.

**Где ставить.** Статическая ссылка «написать нам» в настройках соберёт только вовлечённых —
то есть ровно не тех, кто нужен. Просьба должна приходить в момент недовольства:

- **«Не совсем» под утренним прогнозом** — уже существующий тап, уже сигнал промаха.
  Достаточно follow-up: «расскажешь, что не так?» со ссылкой. Новых механик не нужно.
- **Молчание несколько дней** — повод для пуша (зависит от пункта 4).
- **Выход из онбординга** — технически сложнее, но там самая ценная и самая недоступная
  группа.

Канал [@keegooroomie](https://t.me/keegooroomie) для новостей — отдельно и спокойно,
это не инструмент исследования.

Побочно закрывает требование конкурса «контакты для связи с владельцем решения», которое
сейчас выполнено только на сайте.

### 7. Конфиг с сервера — класть сейчас, иначе не положить никогда

Эндпоинт отдаёт JSON со значениями, приложение их читает и применяет: тексты, пороги,
времена уведомлений, флаги включения уже существующих механик.

Смысл не в самой фиче, а в том, что **ретроспективно её не добавить**. Работает такой
конфиг только для того, что в сборке уже есть, — включить задним числом то, чего в APK
нет, невозможно. Значит каждый пункт, не положенный в 1.1.0, будет ждать следующей
модерации.

Мы и так управляемся с сервера процентов на семьдесят: весь текст (утро, разбор дня,
недельная, follow-up, инсайты) генерится на бэке, промты лежат в слотах с версиями и
переключаются админ-API, сигналы считаются у нас. Релиза требуют только триггеры
уведомлений (`AlarmManager`, на устройстве), разрешения, SDK и структура экранов.
Конфиг сдвигает эту границу в нашу сторону.

Чего делать нельзя: скачивать и исполнять код. Это запрещено правилами магазинов и
само по себе дыра в безопасности. Конфиг — это значения, не поведение.

### 8. Развязать «обновись» и публикацию в сторе

Сейчас `/opt/companion/latest_version` пишет CI по тегу — строки в `release.yml` и
`deploy-backend.yml`. То есть всплывашка «Меня можно обновить» показывается людям в момент
**сборки**, а не публикации. Для 1.0.2 это значило бы: человек видит предложение, жмёт и
попадает в стор, где всё ещё 1.0.0.

Чинится без кода: в `.env` есть `APP_LATEST_VERSION`, который перекрывает файл. Убрать
запись из `release.yml` и ставить значение руками в день, когда RuStore действительно
опубликовал.

Цена бездействия маленькая, но неприятная: предложение обновиться, ведущее в никуда,
обесценивает сам механизм — в следующий раз на него не нажмут.

## Правки и решения 10.11 (меняют пункты выше)

Работа идёт в ветке `push-test`, отдельно от прода. Версию до 1.1.0 / 26 **не поднимаем**,
пока владелец явно не скажет «поднимай».

**Маркер активности (общий для пп. 1 и 9).** Любое из трёх событий создаёт отметку «день
активен» (по ней же считаем DAU): приложение открыто; утреннее уведомление тапнуто или
смахнуто (`deleteIntent`); нажата кнопка в уведомлении. Сейчас в коде нет ни учёта открытий,
ни `deleteIntent` — это нужно завести. Хранится на устройстве.

**П. 1, дневной пуш.** Шлём около 14:00 **только если с утра не было ни одной отметки
активности**. Время — не фиксированное, а «центр ± дельта» (по умолчанию 14:00 ± 1 час), оба
значения приходят из конфига. Тексты нейтральные: «Половина дня прошла. Хочешь увидеть, что
заметно по твоему дню?», «Днём у тебя обычно что-то меняется. Загляни, расскажу что.»;
серверный LLM-текст с бюджетом 7 с, иначе локальный запасной.

**П. 4, серверные пуши.** Канал — RuStore Push напрямую (`vkpns.rustore.ru`), токен приложения
хранится у нас. Проверка доставки — на устройстве владельца в день публикации 1.0.2, чтобы не
задеть модерацию. Ветка `push-test` (коммит `57a8633`) — одноразовая сборка `1.0.2-push`
(versionCode 26) для этой проверки; SDK `pushclient:7.5.0` реально доступен в nexus
(последняя там 7.6.0, карточка консоли с 6.3.0 отстаёт).

**П. 5, онбординг.** Сначала доводим прототип `web/onboarding-reveal` до семи экранов 1 в 1 с
приложением (одна панель, в которой по мере выдачи разрешений что-то проявляется), потом
переносим в приложение.

**П. 6, связь с автором.** Не в «Не совсем». Отдельное место в приложении: почта
spartan.dgs.121@icloud.com; позже — Telegram-бот, который сводит все сообщения в общий чат.
Где именно разместить — решить (профиль, после ответов на вопросы, или отдельный пункт).

**П. 7 и 8, конфиг с сервера.** Состав JSON ещё не определён, должен быть продуман до релиза.
Уже известно: окно дневного пуша (центр и дельта), порог «молчания» в днях, версия для
всплывашки «обновись» (замещает ручную правку `APP_LATEST_VERSION`), тексты и времена
уведомлений, флаги механик.

**П. 9, недельная сводка (пересмотрено).** Остаётся отложенной **для тех, кто взаимодействует**.
Тем, у кого не было ни одной отметки активности 3 дня подряд и больше, недельная сводка
отправляется как повод вернуться. Зависит от маркера активности и серверных пушей (п. 4).

### Ход работ 11.11 (ветка `push-test`, всё 1.1.0 делаем в ней)

**Проверка доставки RuStore Push (на устройстве владельца).** `notification`-пуши доходят (иногда
с задержкой в минуты, пока связь была плохая / включён VPN). Data-only пуши (будить наш процесс)
не дошли ни разу из четырёх, в том числе при открытом приложении; причина не выяснена (телефон
или наш сервис) и дальше не копаем. **Решение: все серверные пуши — типа `notification`.** SDK
рисует их сам, наш процесс не нужен. Дубль (оба показывались дважды) был нашей ошибкой и убран.

**Эндпоинт и хранение токена (п. 4) — написано, не выкачено на сервер:**
- миграция `017_push_tokens.sql`: `users.push_token`, `push_provider`, `push_token_seen_at`;
- `PUT /api/v1/push-token` (auth как у остальных): приложение присылает токен при заходе на
  главный экран и при смене токена; повтор не шлёт запрос, пока токен тот же;
- `internal/push`: клиент RuStore (`vkpns.rustore.ru`) + отправитель; каждая отправка — строка
  `call_log` (`call_type=tool`, `component=push`, `trigger` = `scheduled` для автоматики или
  `admin` для ручной, на успех `user_visible=true`); токен, который провайдер не знает (404),
  сбрасывается;
- `POST /admin/push` (локальный порт): `user_ids` (поимённо, dev допускаются) или `silent_days`
  (зарегистрированные без активности N дней, dev исключены); для сегмента по умолчанию
  `dry_run=true`, то есть только считает аудиторию;
- переменные сервера: `RUSTORE_PUSH_PROJECT_ID`, `RUSTORE_PUSH_TOKEN` (сервисный токен из
  консоли; в репозиторий не класть, в `/opt/companion/.env`). Без них отправка выключена.

**Не сделано по п. 4:** автоматический запуск рассылок (дневной пуш, реактивация по молчанию):
нужен маркер активности (AND-01) и расписание; пока отправка только ручная через `/admin/push`.

**Иконка (pearl-4) внесена в приложение:** адаптивный слой из `pearl-4-1024.png`
(`drawable-nodpi/pearl_foreground.png`), слой для тематических иконок Android 13+,
512×512 для консоли RuStore лежит в `internal-docs/research/icon/pearl/pearl-4-512.png`.
Фиксируется для всех следующих версий.

**AND-01, маркер активности и события (11.11, в коде, не проверено на устройстве).**
- `ActivityMarker` (`data/prefs/ActivityMarker.kt`): на устройстве хранит время и источник
  последнего признака жизни: `open` (приложение открыто), `dismiss` (уведомление смахнуто),
